# 企业经营数据 Agent：求职证据增强设计

## 1. 背景与问题

项目已具备指标词典、Schema 检索、Text-to-SQL、安全校验、图表生成、真实评测和安全评测。当前基础集结果正确率为 71.9%，进阶集为 38.9%，总集为 64.0%。这说明项目已经诚实暴露了单次生成完整 SQL 的能力边界，但产品层仍把“安全执行成功”近似呈现成“答案可信”，也没有收集用户纠错信号。

本轮不继续堆 Prompt 规则，而是把不确定性、受控修复和用户反馈设计进产品。

## 2. 目标

- 为每次查询提供可解释的质量检查、可信度等级和复核提示。
- 对 SQL 校验失败或数据库执行失败执行最多一次受控修复，提高链路可用性。
- 收集用户对结果正确性的反馈，形成可用于扩充评测集的数据入口。
- 消除前端 500KB 以上构建警告，保持作品演示加载轻量。
- 更新 README 和面试材料，展示从“追准确率”转向“管理不确定性”的产品判断。

成功标准：系统不再把所有可执行 SQL 包装成确定事实；用户能判断为什么需要复核，开发者能从反馈中获得下一轮评测样本。

## 3. 范围与非目标

### 本轮范围

- 新增查询质量评估器，输出检查项、等级、原因和是否建议人工复核。
- 新增最多一次的结构性失败修复循环。
- 查询响应新增 `query_id`、`attempt_count`、`confidence`、`needs_review` 和 `quality_checks`。
- 新增反馈 API 与 SQLite 反馈记录。
- 前端展示质量状态并提供“结果正确/需要改进”反馈按钮。
- 对 ECharts 等大依赖做稳定的构建拆包。
- 用现有测试、80 题评测结构和安全用例回归。

### 明确不做

- 不宣称可信度等级等于统计校准后的正确概率。
- 不使用 LLM Chain-of-Thought，也不向前端暴露内部 Prompt。
- 不做多租户、企业 SSO、云部署或生产级数据接入。
- 不增加第二个模型供应商，不进行无上限重试。
- 不再通过追加长 Prompt 规则追逐单次评测波动。

## 4. 架构与组件

### 4.1 查询质量评估器

新增独立、确定性的 `QueryQualityAssessor`。它只读取问题、指标匹配结果、安全检查结果、规范化 SQL、查询行数和展示形态，输出：

```text
quality
├── confidence       high / medium / low
├── needs_review     boolean
└── checks[]
    ├── code         稳定机器码
    ├── passed       boolean
    └── message      面向用户的简短说明
```

第一版检查项：

- `metric_grounded`：问题涉及业务指标时是否命中指标词典。
- `sql_safe`：SQL 是否通过 AST、安全表列和只读校验。
- `result_non_empty`：结果是否非空；空结果不等于错误，但需要提示。
- `shape_matches_intent`：KPI、排行、趋势等结果列形状是否符合展示意图。
- `advanced_query`：同比、环比、复购分层、多事实关联等高难模式是否命中。
- `safety_rewritten`：是否发生 LIMIT 注入或钳制。

可信度是规则化的产品提示：出现结构错误或高难模式为低；存在空结果、改写或弱指标匹配为中；所有基础检查通过为高。文案明确“这是检查等级，不是正确率概率”。

### 4.2 受控修复循环

查询服务由一次直线调用改为最多两次尝试：

```text
生成 SQL
  → 安全校验
  → 执行
  ├─ 成功：进入质量评估
  └─ 结构性失败：携带机器可读错误修复一次
       → 再次安全校验与执行
       ├─ 成功：attempt_count = 2
       └─ 失败：返回原有错误类型，不再重试
```

只对 `SQLValidationError` 和 `sqlite3.Error` 修复；网络错误、认证错误、模型拒答和未知异常不重试。第二次生成上下文包含原 SQL 与违规码或数据库错误摘要，不包含数据库数据行。Mock 客户端提供确定性行为，保证离线测试不访问网络。

### 4.3 用户反馈闭环

每次成功查询生成随机 `query_id`。反馈接口只接受：

- `query_id`
- `rating`：`correct` 或 `incorrect`
- 可选短文本 `comment`，长度受限

SQLite 表记录问题、最终 SQL、质量等级、尝试次数、反馈和时间。API 不接受客户端回传 SQL 或问题正文，避免篡改审计上下文。重复反馈按 `query_id` 更新，便于用户修正选择。

反馈数据不自动进入评测集。进入评测集前必须人工审核问题口径和 golden SQL，避免把用户噪声直接变成标签。

### 4.4 前端可信度体验

结果区增加“质量状态”卡：

- 高：基础检查通过，仍提示业务决策需核对来源。
- 中：展示具体提醒，例如空结果或查询被 LIMIT 改写。
- 低：突出“建议人工复核”，并列出高难查询等原因。

结果下方提供两个反馈按钮。提交成功后锁定为当前选择，允许切换一次；失败时保留结果并提示反馈未保存。

### 4.5 构建拆包

在 Vite 的 Rollup 配置中把 Vue、ECharts 与图标库拆为稳定 vendor chunk。验收以生产构建不再出现 500KB 单 chunk 警告为准，不通过简单调高警告阈值掩盖问题。

## 5. 数据流

```text
自然语言问题
  → 指标词典 + 相关 Schema
  → LLM 生成 SQL
  → AST/表列/只读安全校验
  → SQLite 执行
  → [结构失败时最多修复一次]
  → 质量评估器
  → 结论 + 图表 + SQL + 质量状态
  → 用户反馈
  → feedback 表
  → 人工审核后进入未来评测候选
```

## 6. 错误与安全处理

- 重试上限固定为一次，任何路径都不能形成循环。
- 修复后的 SQL 必须重新走完整安全校验，不能直接执行。
- 数据库错误只向模型提供错误类别和脱敏摘要，不提供数据内容。
- 质量评估器异常时默认 `confidence=low`、`needs_review=true`，查询结果仍可显示。
- 反馈接口校验 query_id、枚举值和文本长度；未知 query_id 返回 404。
- 前端健康检查、查询错误和反馈错误互相独立，反馈失败不能清空查询结果。

## 7. 测试与验收

- 单测覆盖质量等级映射、每项检查、异常时 fail-safe 行为。
- 单测覆盖首次成功、校验失败后修复成功、执行失败后修复成功、第二次失败停止、网络错误不重试。
- API 测试覆盖新增响应字段、正确反馈、重复更新、非法 rating、未知 query_id。
- 安全测试确认修复 SQL 仍经过校验，危险 SQL 无法借重试绕过。
- 既有 66 个测试全部通过，新增测试全部通过。
- 前端生产构建通过且无 500KB 单 chunk 警告。
- 现有 60/20/80 评测口径保持不变；若没有重新运行真实模型，不更新真实准确率数字。

## 8. 求职叙事

项目最终突出四个面试信号：

1. 我用真实 80 题发现 Prompt 微调在 64% 附近到达天花板，因此停止堆规则。
2. 我把模型的不确定性变成用户可理解的质量等级和人工复核提示。
3. 我只对结构性失败做一次受控修复，并让修复结果重新经过安全校验。
4. 我把用户反馈存为待审核数据，而不是直接污染评测集，建立可持续的数据闭环。

## 9. 实施顺序

1. 质量评估器、返回契约与单测。
2. 受控修复循环与安全回归。
3. 反馈数据模型、API 与测试。
4. 前端质量卡、反馈交互和构建拆包。
5. README、面试讲解文档与全量验证。

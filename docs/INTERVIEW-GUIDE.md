# 企业经营数据 Agent：面试讲解卡

## 30 秒版本

这是一个面向经营分析的 Text-to-SQL Agent。它把自然语言问题映射到指标词典和相关 Schema，生成 SQL 后经过 SQLGlot AST、表列白名单、只读限制和 LIMIT 控制，再查询 SQLite，输出结论、图表和明细。我用 80 道真实问题评测发现基础题正确率 71.9%、进阶题只有 38.9%，所以没有继续堆 Prompt，而是增加了透明的质量等级、最多一次受控修复和用户反馈闭环。

## 为什么这个项目不是普通 NL2SQL Demo

- 指标名称不直接当字段名，而是由 YAML 指标词典展开业务口径。
- 业务数据库连接强制 `PRAGMA query_only`，模型生成 SQL 还必须通过 AST 与表列校验。
- 修复只针对结构性失败、最多一次，修复结果不能绕过安全校验。
- 前端明确显示检查等级和复核原因，不把“SQL 能执行”包装成“业务答案一定正确”。
- 用户反馈写入独立侧库，必须人工审核后才能进入评测候选。

## 最值得讲的失败

早期在 20 题上达到过 95%，扩到 80 题后跌到约 64%。进一步分析发现两件事：第一，长 Prompt 继续加规则会修好一些题，同时让另一些题退化；第二，6 道 golden SQL 存在 SQLite 整数除法问题，模型给出正确浮点结果反而被判错。我的处理是修复评测数据、拆成基础 60 题和进阶 20 题，并停止用小样本高分证明能力。

## 关键取舍

### 为什么不用模型自己给置信度

模型自报分数通常没有校准依据。当前等级来自可解释的确定性检查，例如指标是否命中、高难模式、结果是否为空、结构是否匹配和安全层是否钳制。它不是正确率概率，但能告诉用户为什么要复核。

### 为什么只重试一次

无限 Agent 循环会放大成本、延迟和安全风险。一次修复足以证明系统能利用校验反馈恢复常见结构错误；第二次仍失败就显式返回错误。

### 为什么反馈不自动训练或写入评测集

用户反馈可能包含误解、口径冲突或恶意内容。先存成待审核数据，确认问题定义和 golden SQL 后再进入评测集，避免数据飞轮变成噪声飞轮。

## 可直接回答的追问

- 当前瓶颈：同比环比、复购分层、多事实关联等需要多步分解的查询。
- 下一步：把高难问题拆成查询计划、子查询生成、结果校验三个阶段，并只在低质量等级时触发。
- 当前安全边界：只验证了模拟数据和 25 条攻击样本，不能据此声称生产级或绝对安全。
- 生产化还缺什么：企业鉴权、多租户隔离、真实数据源权限、查询成本控制、指标血缘和监控告警。

## 演示顺序

1. 提一个基础销售额问题，展示高等级检查、图表、明细和 SQL。
2. 提一个环比或复购问题，展示低等级与人工复核提示。
3. 展示危险 SQL 被拦截，说明修复结果也必须重新校验。
4. 点击“结果正确/需要改进”，说明反馈进入人工审核队列。
5. 打开 60/20 评测结果，解释为什么不使用 20 题 95% 作为项目成绩。

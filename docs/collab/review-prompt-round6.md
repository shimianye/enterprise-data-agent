## 3. 为什么 Patch 没显著提升

### 3.1 LLM stochastic 噪声
真实 LLM 单次跑 ±3-4 题波动是真实的（80 题 5% = 4 题）。6 修 7 错基本在噪声范围内。

### 3.2 Patch 副作用（重要）
- **rule 16（聚合正确性）过严**：模型现在倾向对所有比率加 `* 1.0`、对所有 CASE 用 `COUNT(DISTINCT CASE...)`，
 但有些题 golden 故意用 `SUM(CASE...)/COUNT(*)` 形式（无 * 1.0）
- **rule 8（输出形状）模型过拟合**：Q007 v6 模型以为必须"输出最简"，加了 WITH 子查询反而多列
- **rule 14（JOIN 完整性）部分生效但不够强**：Q025/Q062 仍用 `customers.city` 替 `stores.city`、仍用 `order_items AS p` 替 `products`

### 3.3 17 条 rules 太长
12 → 17 条后，单条规则的"注意力"被进一步稀释。Few-shot 6 条的权重也被冲淡。

### 3.4 评测集设计的问题（重要反思）
**80 题里有 8-10 道 golden_sql 本身就过难**，比如：
- Q007：WITH + 多表 JOIN + 增长率计算 + LIMIT 1（应拆 3 子问题）
- Q033：复购率的标准公式（COUNT(DISTINCT order_id) per customer → CASE）模型几乎永远写不出
- Q051：跨年 H1 同比（需要 scalar subquery × 2）+ 利润字段选择
- Q056/Q057：复购/客户分层（多层子查询 + CASE WHEN BETWEEN）
- Q068：ROI（NULLIF + ratio + JOIN promotions）
- Q071：品类退款率（LEFT JOIN + CASE WHEN EXISTS）+ 比率
- Q073/Q079：退款×售后关联（EXISTS + 比率）

这些是**真实业务复杂查询**，对 LLM 来说是 SOTA 级难题。**期望 LLM 一次性写对是过高的**——人类分析师也要 5-15 分钟。

## 4. 三个选项

### 选项 A：接受 v6 = 61.3%，README 选 C 展示真实数字（v4 95% / v5 62.7% / v6 61.3%）

**优点**：
- 诚实
- v6 比 v5 链路失败更少（5→4），SQL 可执行率上升
- 6 题真修复可作为"Prompt 演进价值"的证据

**缺点**：
- 数字看起来在迭代且未达 80% 目标
- 面试官可能问"为什么 patch 没显著提升"

**README 表述建议**：
```
| 真实 LLM 评测 | 题量 | 结果正确率 | 备注 |
|---|---|---|---|
| v4 (迭代收敛点) | 20 | 95% | 在 20 题上 4 轮迭代的最优 baseline |
| v5 (扩到 80 题) | 80 | 62.7% | 暴露 5 类 prompt 边界问题（诊断基线）|
| v6 (5 类 patch 后) | 80 | 61.3% | 修了 6 题，但 patch 副作用抵消（详见 docs/evaluation-history.md）|
```

### 选项 B：撤回部分 patch，缩小规则集（rule 14/16 部分删除）

策略：
- **保留**：rule 13（字段归属）、rule 15（事实表归属）、rule 17（时间锚定）— 这三类真有修复且无副作用
- **撤回**：rule 14（JOIN 完整性，rule 12 已部分覆盖）、rule 16（聚合正确性，副作用大于收益）
- **保留** 17 → 15 条（去掉 14 和 16）

预估：v7 = 65-70%（去掉规则 16 后 Q009/Q012/Q014/Q020 不再被错）

### 选项 C：重审评测集，承认 80 题里有"超 LLM 能力"的题

策略：
- 把 80 题分成"基线 60 题（人类标准）+ 进阶 20 题（专家级）"
- README 主指标用 60 题基线，预期能到 75-85%
- 20 道进阶题单独标注"专家级，仅供 LLM 能力上限参考"

预估：基线 60 题真实评测 = 70-80%
